# Prometheus Scrape & Alerting Guide — HSM Resharding (Track 42)

This document shows recommended Prometheus scrape configuration and example alerts for the Track 42 resharding metrics added to the `ai-platform` service.

## Exposed Metrics

- `hsm_reshard_ops_total` (Counter): number of generated resharded shares (incremented per generated target share).
- `hsm_reshard_latency_seconds` (Histogram): observed latency for the reshard operation (seconds). Buckets: `[0.001, 0.01, 0.1, 1, 5]` by default.

## Scrape Configuration (Prometheus `prometheus.yml`)

Add a scrape job that targets the service endpoint exposing `/metrics`. The service protects `/metrics` using bearer token + CIDR whitelist; use `bearer_token_file` and network-level access controls in your deployment.

```yaml
scrape_configs:
  - job_name: "ai-platform-hsm"
    metrics_path: /metrics
    static_configs:
      - targets: ["ai-platform.internal:3003"]
    # Use a file containing the bearer token (mounted from a secret)
    bearer_token_file: /etc/prometheus/secrets/hsm_bearer_token
    # Optional: limit which labels Prometheus attaches
    relabel_configs:
      - source_labels: [__address__]
        target_label: instance
        replacement: ai-platform-hsm
```

Notes:

- Ensure the node or scrape target IP is within the service CIDR whitelist configured by the HSM metrics auth middleware.
- Use short `scrape_interval` (e.g. 15s) if you need fine-grained latency dashboards; alerts below assume 5m evaluation windows.

## Example Alerting Rules

Place these in your Alertmanager rules file (or a PrometheusRule CRD in Kubernetes). Adjust thresholds to match your SLO.

### 95th-percentile latency spike (reshard)

```yaml
- alert: HSMReshardHighLatency
  expr: histogram_quantile(0.95, sum(rate(hsm_reshard_latency_seconds_bucket[5m])) by (le)) > 1
  for: 10m
  labels:
    severity: page
  annotations:
    summary: "HSM reshard 95p latency > 1s"
    description: "95th percentile reshard latency over 5m is > 1s. Investigate resharding load and attestation delays."
```

### Reshard operations stopped or dropped below expected rate

```yaml
- alert: HSMReshardOpsLowRate
  expr: rate(hsm_reshard_ops_total[5m]) < 0.1
  for: 15m
  labels:
    severity: warning
  annotations:
    summary: "Low HSM reshard operation rate"
    description: "Reshard operations per 5m < 0.1; check scheduler, attestation failures, or crash loops."
```

### Scraping or endpoint availability problem

```yaml
- alert: PrometheusScrapeDown_ai_platform_hsm
  expr: up{job="ai-platform-hsm"} == 0
  for: 5m
  labels:
    severity: page
  annotations:
    summary: "Prometheus cannot scrape ai-platform HSM metrics"
    description: "Prometheus reports the target as down for 5m. Verify bearer token, network ACLs, and service health."
```

## Runbook / Triage Steps

- Check `up{job="ai-platform-hsm"}` and `hsm_reshard_ops_total` timeseries to confirm scraping.
- Confirm Prometheus uses the correct `bearer_token_file` and the token matches the deployment secret.
- If latency alerts trigger: inspect service logs for attestation delays, DB connection stalls, or CPU saturation.
- If ops rate drops: verify scheduler tasks, confirm attestation client connectivity, and check for exceptions in `GroupReshardEngine` audit events.

## Recommended Future Enhancements

- Export a dedicated `hsm_reshard_errors_total` counter for ratchet/reshard failures to allow precise error-rate alerting.
- Add labels to `hsm_reshard_ops_total` (e.g., `old_size`, `new_size`) to improve capacity dashboards and per-policy slicing.
