Authoring Custom Enterprise Compliance Guardrails

Version: draft

Date: 2026-07-30

---

Purpose

This guide explains how engineering teams and internal AppSec reviewers can author, register, and validate enterprise-specific guardrails for SimpleBeacon. Guardrails are first-class rule modules that the analyzer pipeline loads alongside built-in rule manifests. Custom guardrails can be simple regex-based detectors for high-velocity patterns or full AST walkers for robust, context-aware detections. Guardrails may optionally provide deterministic remediation fixes that wire into the remediate subcommand.

Directory & Loading

  • Local rules directory (per-repo): ./.simplebeacon/rules/
  • Built-in rules remain in the package under packages/simplebeacon-cli/src/rules/.
  • Runtime load order: local rules (repo) → organization/airgap rules → built-in rules. Local rules override built-in matches by id.

Rule module shape (minimal example)

Each rule is a CommonJS module exporting an object (or array of objects). Required top-level keys:

  • id (string): unique identifier, e.g. ENT-SEC-001.
  • name (string): human title.
  • severity ("low"|"medium"|"high").
  • impact ("low"|"medium"|"high").
  • likelihood ("low"|"medium"|"high").
  • category (string): grouping.
  • description (string): short description.
  • matcher (object): defines the detection strategy (see Section: matcher types).
  • fix (optional object): deterministic remediation instructions (see Section: remediation).

Example rule module (regex)


module.exports = {
  id: 'ENT-SEC-001',
  name: 'Restricted Internal Model API',
  severity: 'high',
  impact: 'high',
  likelihood: 'medium',
  category: 'Enterprise Governance',
  description: 'Detects unapproved internal model access endpoints.',
  matcher: {
    type: 'regex',
    pattern: /(gpt-4-32k|claude-2\.1|unapprovedModelAPI)/g,
    paths: ['**/*.js', '**/*.ts']
  },
  guidance: 'Replace with secureModelProxyGateway and run `npx simplebeacon remediate` to apply fixes.'
};

Matcher types

1) Regex matcher (fast)

  • matcher.type = 'regex'
  • matcher.pattern: string or RegExp
  • matcher.flags: optional (e.g., i)
  • matcher.paths: glob(s) to limit scanning (defaults to project file globs)

Engine behavior: run a file-level test using the RegExp; on match, produce a finding with file/line snippet and matched groups.

2) AST walker (robust)

  • matcher.type = 'ast'
  • matcher.language: javascript | typescript | python (future)
  • matcher.visitor: function or object implementing node visitors (see example)

AST walker example (JavaScript):


// rule-ast-unapproved-client.js
const { parse } = require('@babel/parser');
module.exports = {
  id: 'ENT-SEC-010',
  name: 'Unapproved Model Client Instantiation',
  severity: 'high',
  matcher: {
    type: 'ast',
    language: 'javascript',
    visitor: function({ ast, file, report }) {
      const traverse = require('@babel/traverse').default;
      traverse(ast, {
        CallExpression(path) {
          const callee = path.get('callee');
          if (callee.isMemberExpression()) {
            const object = callee.get('object');
            const prop = callee.get('property');
            if (object.isIdentifier({ name: 'unapprovedModelAPI' })) {
              report({
                message: 'Calls to unapprovedModelAPI detected',
                file,
                node: path.node
              });
            }
          }
        }
      });
    }
  }
};

Notes on AST rules

  • The analyzer will parse files using Babel (JS/TS). Your visitor receives a parsed ast and a report callback. Use @babel/traverse helpers for robust matching.
  • Keep visitors deterministic and avoid long-running CPU loops; prefer structural checks instead of fuzzy text searches in AST mode.

Authoring deterministic remediation fixes

Rules may include a fix object that the remediate subcommand understands and can apply automatically or in an interactive preview mode.

Supported fix types (current):

  • replace — simple RegExp-based text replacement with file/line context.
  • ast-transform — a JS function that returns a modified AST; the CLI will serialize back using @babel/generator.

Example fix (string replace):


fix: {
  type: 'replace',
  pattern: /unapprovedModelAPI\.create\(/g,
  replacement: 'secureModelProxyGateway.create('
}

Example fix (AST transform shim):


fix: {
  type: 'ast-transform',
  transform: function({ ast, node }) {
    // mutate AST nodes deterministically; return true if modified
  }
}

Testing & Local validation lifecycle

1. Drop your rule file(s) into ./.simplebeacon/rules/.

2. Run a local scan including custom rules:


npx simplebeacon scan --rules-dir=./.simplebeacon/rules --offline --output ./.simplebeacon/report.json --full

3. Use --dry-run with remediate to preview fixes:


npx simplebeacon remediate --rules-dir=./.simplebeacon/rules --dry-run

4. Unit testing rules

We recommend a small Jest harness inside your repository to assert rule behavior. Example test scaffold: ./.simplebeacon/rules/__tests__/rule-ENT-SEC-001.test.js


const { runRuleOnString } = require('simplebeacon-cli/test-utils');
const rule = require('../my-rule.js');

test('flags unapproved model name', async () => {
  const res = await runRuleOnString(rule, 'const x = unapprovedModelAPI.create("foo");', 'test.js');
  expect(res.findings.length).toBeGreaterThan(0);
});

Registration & packaging

  • No build step required for simple JS rules: drop them in ./.simplebeacon/rules/ and re-run a scan.
  • For organization-wide rule distribution, place rules in an internal package and instruct CI to copy them into the repo's .simplebeacon/rules/ during pipeline setup.

Best practices & conventions

  • Rule id format: ORG-AREA-### (e.g., ACME-AUTH-001). Keep ids stable.
  • Keep rules small and focused (single responsibility): one pattern → one rule.
  • Add tests next to rule files and wire them into CI.
  • Document each rule with an internal severity rationale and sample false-positive cases.
  • Avoid aggressive fix logic that could break runtime behavior; remediation should be safe & reversible.

CI tips

  • Add a CI step to validate rules:

- Run static sanity (node -c / npm run lint) on rule files.

- Execute rule unit tests.

- Run a quick npx simplebeacon scan --rules-dir=./.simplebeacon/rules --offline --output /tmp/r.json --full on a small fixture set.

Troubleshooting

  • If your regex rule produces too many false positives, restrict with matcher.paths or add contextual heuristics (e.g., require surrounding token anchors).
  • If an AST rule is slow, reduce visited node types and prefer path.get() style checks to avoid full subtree traversals.

Appendix: Example rule set

  • ent-restrict-models.js — regex for banned model names.
  • ent-block-secret-literals.js — AST walker that flags string literals in code assigned to apiKey variables.
  • ent-replace-unapproved-client.fix.js — optional AST transform fix for client replacement.
