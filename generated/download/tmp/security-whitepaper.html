1. Executive Privacy Guarantee & The Cloud Harvest Problem

Problem definition

Conventional cloud-hosted code scanners and AI-assisted code review tools commonly ingest, persist, and centralize developer inputs and entire code artifacts. Those inputs are often used to train or improve models, or are otherwise retained in vendor systems. For high-value corporate IP and regulated data, this creates unacceptable leakage risk and can violate data residency, confidentiality, or contractual obligations.

SimpleBeacon stance: Zero-Telemetry Guarantee

  • No telemetry by default: SimpleBeacon does not phone home, upload source, create persistent server-side telemetry, or send rule matches to third-party services.
  • Local-first processing: All analysis, rule evaluation, and artifact generation occurs on the local host or within explicitly provisioned local runtime containers under the customer's control.
  • Explicit opt-in only: Any feature that transmits data externally is opt-in, audited, and disabled by default; enterprise customers may restrict or remove opt-in paths entirely.

Risk mitigation assurances

  • Data residency: No code, diffs, or findings are transmitted to any cloud services by default.
  • Deterministic local artifacts: All reports and certificates are generated locally and can be archived on customer storage systems.
  • Auditable controls: The product ships with forensic hashes and reproducible report generation steps that allow independent verification.

2. Local Execution Engine Sandbox & Node Architecture

Overview

SimpleBeacon is intentionally engineered to run entirely on the customer's infrastructure (developer laptop, CI runner, or air-gapped appliance). The architecture separates short-lived analysis workers (Node/V8 processes) from optional UI renderers (local HTTP server or embedded WebView) and enforces strict boundaries for filesystem, network, and in-memory state.

High-level components

  • CLI orchestration: npx simplebeacon or an installed binary — spawns one or more ephemeral worker processes to perform parser/analysis workloads and collates deterministic outputs into ./.simplebeacon/report.json and final PDF certificates.
  • Analyzer engines: Static, package-bundled rule sets implemented as JS/TS modules (AST matchers, regex signatures, structural heuristics). Rules are loaded from the local package and are not fetched at runtime unless the operator explicitly runs an update command.
  • Local UI: A lightweight local HTTP server bound to loopback (or an embedded VS Code WebView) serves static UI assets from disk. The UI reads analysis results from local artifact files only.
  • Persistence: Intermediate state uses ephemeral tempfiles; final artifacts are written atomically to the .simplebeacon directory.

V8 / Node process sandboxing and isolation

  • Unprivileged worker processes: The core analysis runs inside dedicated Node (V8) worker processes that are spawned with the invoking user’s identity. No elevated privileges are required or requested by default.
  • Controlled syscalls and read-only parsing policy: Analyzer workers are implemented to restrict write-access during parsing phases — the common pattern is "read-only parse" -> "analyze in-memory" -> "write final artifact". Intermediate files are written only to explicitly configured temp folders and are removed on process exit.
  • Worker lifetime and restart policy: Each analysis run creates new worker processes; long-lived daemons are opt-in. Worker lifetimes are short and deterministic to avoid leaking in-memory state across runs.
  • Optional OS-level sandboxing: Operators may run SimpleBeacon inside OS-level sandboxing tools (containers, firejail, Windows AppContainer) for an additional isolation layer; the application design does not require these but is compatible with them.

Volatile in-memory cache matrix & State Containment Rule

  • createXStore() factory model: All modules that previously exposed module-scoped mutable singletons now provide factory constructors (for example createEventStore(options)). The expected usage pattern is to create per-run instances and discard them at the end of the run so no state persists between invocations.
  • Ephemeral caches only: In-memory caches (rule match caches, parsed-AST caches, temporary indexers) live only in worker process memory and are not persisted unless explicitly saved by an opt-in persistence API. By default caches are volatile and eligible for GC when the process exits.
  • Deterministic cleanup: Stores implement a close()/dispose() API that clears internal maps and releases file handles; test suites and the CLI call these lifecycle hooks at the end of each run.
  • Proof-of-zero-history: The combination of per-run worker processes, factory-instantiated stores, and explicit disposal means that after a run completes and worker processes exit, there are no in-memory artifacts retained on disk or in process-resident heaps accessible to subsequent runs.

Localhost network binding boundaries

  • Loopback-only UI binding: The default local dashboard server binds explicitly to 127.0.0.1 and ::1 (configurable) and never listens on 0.0.0.0 or external interfaces unless the operator explicitly overrides the binding configuration.
  • Explicit opt-in for remote APIs: Any feature that would contact external services (rule update checks, telemetry, remote model inference) is disabled by default and gated behind an --enable-remote/--telemetry flag which documents the data flow and adds an explicit consent confirmation in the UI.
  • Hardened HTTP headers and CORS: The local server sets restrictive CORS, Content-Security-Policy, and X-Frame-Options headers to eliminate inadvertent remote-content inclusion when running in a browser or WebView.

Controlled file I/O and atomic writes

  • Write-then-rename commit: Final artifacts (for example report.json) are written to a temporary file in the same filesystem namespace then atomically renamed into place. This ensures either the previous artifact or the new artifact is present, never a partially-written file.
  • EPERM-aware Windows fallback: On Windows where rename can fail with EPERM under antivirus contention, the implementation falls back to a synchronous copy-and-replace strategy that preserves atomicity guarantees from the operator’s point of view.

Developer hygiene rules (enforced via CONTRIBUTING.md)

  • No module-level mutable caches for per-run data; prefer factory constructors and explicit lifecycle methods.
  • Persisted caches require explicit opt-in and must be located under ./.simplebeacon/cache with TTL and clear() semantics.
  • Tests must instantiate isolated factories for stores and call lifecycle dispose() methods; CI runs validate the absence of process-global singletons for per-run state.

Operational recommendations

  • Run CLI in --offline mode for forensically auditable runs.
  • Use OS-level sandboxing for sensitive environments; enable mounting of repository directories read-only where possible.
  • Periodically run the included self-audit command that verifies loopback binding and absence of outbound connections (see Section 5).

3. Verifiable Network Isolation (The Forensic Proof)

Air-gapped execution

  • Full offline mode: SimpleBeacon provides a --offline/--airgap mode that disables any attempt to retrieve remote rule updates, remote model checks, or online lookups.
  • Dependency validation without network: For supply-chain checks, SimpleBeacon inspects local lockfiles (e.g., package-lock.json, yarn.lock) and package metadata present in the repository copy. No network registry queries are performed in --offline mode.

Local rule manifests

  • All signature rule sets (OWASP LLM Top 10, EU AI Act profiles, etc.) are compiled into static JSON/TS arrays at publish time and bundled with the package.
  • Rule update model: Updates are published as package versions; enterprises may pull updates to an internal artifact repository (no outbound call required during scan).

Forensic proofing primitives

  • Execution trace log: Each run emits a time-stamped trace of analyzer steps and rule matches into an append-only local audit log.
  • Snapshot hashing: Before analysis, SimpleBeacon optionally hashes the repository snapshot (configurable path subset) using SHA-256; the hash is included in the report and embedded into the PDF certificate.
  • Reproducibility: The same CLI invocation on the same input produces the same report hash and artifact set (given identical package version of analyzers).

Supply chain sovereignty

  • Verified artifacts: The engine performs integrity checks against locally stored package checksums for any bundled analyzer components.
  • No remote registry contact: Unless the operator explicitly runs a fetch or update command, the scanner will not contact npm or other registries.

4. Signed Forensic Audits & Regulatory Safe Harbors

Cryptographic ledger integrity

  • Report structure: report.json contains canonical leaves including report.summary, report.findings, and report.remediation with { total, applied, failed, results }.
  • Snapshot hash: A SHA-256 digest is computed over a deterministic canonical serialization of the repository snapshot and the report.json audit log.
  • Certificate signing: Optionally, enterprise customers can sign generated PDFs and JSON snapshots using their local HSM/PKI keys (the CLI supports a --sign-with=path/to/key option that attaches an RFC 7515 JWS signature to the artifact).

Regulatory mapping & safe harbors

  • EU AI Act mapping: Reports include structured metadata tying rule matches to EU AI Act clauses. Executive summaries highlight severity and recommended remediation steps for governance review.
  • Audit-ready exports: The compiled PDF certificate includes: snapshot hash, rule manifest version, CLI package version, analysis timestamp, and a human-readable ledger of findings suitable for legal review.

5. CISO Network Verification Guide (Operational checks)

We included an operational guide that CISO/NetSec teams can execute to independently verify that SimpleBeacon performs no outbound network calls during a scan.

Recommended steps (Windows)

1. Prepare: open an elevated PowerShell session and a second terminal for the scan.

2. Capture baseline sockets:


Get-NetTCPConnection | Sort-Object State, RemoteAddress | Out-File baseline-sockets.txt

3. Start a packet capture (Wireshark) on the host's primary interface. Save capture file to scan-cap.pcap.

4. Run SimpleBeacon in offline mode:


Set-Location C:\path\to\repo
npx simplebeacon --offline --output ./.simplebeacon/report.json

5. Stop capture and verify:

  • Inspect scan-cap.pcap for any outbound IPs other than loopback or local private ranges. Filter example in Wireshark: !(ip.addr == 127.0.0.1 || ip.addr == ::1) and look for any packets.
  • Cross-check socket snapshot diffs:


Get-NetTCPConnection | Sort-Object State, RemoteAddress | Out-File after-sockets.txt
Compare-Object (Get-Content baseline-sockets.txt) (Get-Content after-sockets.txt)

No differences aside from ephemeral OS housekeeping indicate no new outbound connections.

Recommended steps (Linux/macOS)

1. Baseline sockets:


ss -tuna > baseline-sockets.txt

2. Start tcpdump capture:


sudo tcpdump -w scan-cap.pcap not port 22

3. Run the scan in offline mode:


cd /path/to/repo
npx simplebeacon --offline --output ./.simplebeacon/report.json

4. Stop tcpdump and analyze with Wireshark; also diff socket lists:


ss -tuna > after-sockets.txt
diff -u baseline-sockets.txt after-sockets.txt

Interpretation guidance

  • Legitimate loopback traffic and ephemeral OS services are expected; flag any remote IP outside private/corp ranges.
  • If any outbound traffic is observed, collect process details (on Windows: Get-Process -Id ; on Linux: ps -p -o pid,cmd) and contact vendor support. By design normal SimpleBeacon runs should not yield outbound artifacts.

Automation & reproducible proofs

  • The enterprise may run an automated CI job that runs the above commands in an isolated runner and produces an attestation file (network-attestation.json) that records baseline, after, and pcap hashes.
