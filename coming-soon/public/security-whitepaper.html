1. Architecture Overview

SimpleBeacon operates on a local-first execution model with three distinct scanning surfaces, all of which process source code entirely on the client's machine:

  • VS Code Extension (AI Slop Cop): Runs as a VS Code extension that shells out to the local CLI binary. No cloud API is invoked for scanning. Real-time IDE squiggles are generated by local regex and AST rules.
  • CLI Scanner: A standalone binary that reads files from the local filesystem. Performs 48 analyzer module scans (AST parsing, regex matching, dependency analysis) entirely in-process. No network calls are made unless the user explicitly passes --upload to generate a certificate.
  • Browser Sandbox: A WebAssembly-based scanner that runs in the browser's memory sandbox. Files are read via the File System Access API or drag-and-drop. All processing occurs in the browser's JavaScript runtime. The sandbox is wiped when the tab closes.

2. Browser Sandbox Architecture

Execution Model

The browser sandbox scanner operates within the following constraints:

  • Files are loaded via FileReader or showOpenFilePicker() (File System Access API).
  • All scanning logic executes in the main thread or a Web Worker. No fetch(), XMLHttpRequest, or WebSocket calls are made with file contents.
  • Scan results are rendered in the DOM and optionally downloaded as JSON/PDF by the user.
  • The browser's Same-Origin Policy and CSP headers provide defense-in-depth against accidental exfiltration.

Memory Isolation

The browser sandbox inherits the browser engine's process isolation. File contents exist only in the scanner tab's memory space. When the tab is closed, the OS reclaims the memory. No persistence to IndexedDB, localStorage, or cookies occurs for file contents.

3. CLI Scanner Architecture

Network Behavior

The CLI scanner (simplebeacon scan) is designed to avoid source-code upload. Use offline or air-gapped mode when zero network activity is required:

  • Offline mode: Zero network requests. All file I/O is local filesystem reads.
  • License validation: Performed locally using HMAC-SHA256 token verification. No license server contact required.
  • Online paid CI telemetry: Aggregate scan metrics may be sent for team dashboards. No source files, paths, or snippets are included. Use --offline or --air-gapped to disable network activity.

Dependency Analysis

Dependency scanning reads package.json, Cargo.toml, requirements.txt, and other manifest files locally. CVE matching is performed against a locally cached vulnerability database that is updated via a separate simplebeacon update command (not during scans).

4. Content Security Policy Enforcement

SimpleBeacon's production site enforces strict Content Security Policy headers on all pages, including static HTML:

Content-Security-Policy:
  default-src 'self';
  script-src 'self' 'unsafe-inline'
    https://static.cloudflareinsights.com
    https://*.cloudflareinsights.com
    https://cdn.jsdelivr.net
    https://js.stripe.com
    https://api.stripe.com;
  connect-src 'self'
    https://simplebeacon.ai
    https://*.simplebeacon.ai
    https://cascadeprojects-yzzd.onrender.com
    https://*.onrender.com
    https://cloudflareinsights.com
    https://*.cloudflareinsights.com
    https://api.stripe.com
    https://js.stripe.com
    http://127.0.0.1:*
    http://localhost:*
    https://localhost:*;
  object-src 'none';
  frame-ancestors 'self'
    https://simplebeacon.ai
    vscode-webview:
    https://simplebeacon.netlify.app;

Key Restrictions

  • connect-src is restricted to SimpleBeacon's own domain, the API backend (onrender.com), Stripe (billing), and Cloudflare Insights (analytics). No wildcard origins that could allow data exfiltration.
  • object-src 'none' blocks all plugins and embedded objects.
  • frame-ancestors prevents the site from being embedded by unauthorized domains.
  • Any violation of this policy is logged to the browser console and reported via Cloudflare Insights, providing real-time detection of attempted exfiltration.

Verification Command

curl -I https://simplebeacon.ai/dashboard/

This will return the CSP header in the response, which client security teams can compare against the policy documented above.

5. Deterministic Routing (_routes.json)

SimpleBeacon's Cloudflare Pages deployment uses _routes.json to explicitly isolate which paths are handled by serverless functions versus served as static assets:

{
  "version": 1,
  "include": ["/api/*", "/dashboard/*", "/app/*"],
  "exclude": ["/js/*", "/js-es2018/*", "/css/*", ...]
}
  • Serverless paths (include): Only /api/* (auth, billing, config), /dashboard/* (SPA), and /app/* (SPA) are routed to backend functions.
  • Static paths (exclude): All JavaScript (/js-es2018/*), CSS, fonts, and static HTML are served directly from the CDN edge with no server-side processing.
  • This means the scanning JavaScript that runs in the browser is served as a static file and executes entirely in the client context.

6. Network Audit Methodology

Client security teams can independently verify zero data egress using standard network monitoring tools:

6.1 Browser DevTools Network Audit

  1. Open Chrome or Firefox Developer Tools (F12).
  2. Navigate to the Network tab.
  3. Visit https://simplebeacon.ai/audit and initiate a scan.
  4. Filter by Fetch/XHR requests.
  5. Observe: only static asset loads (JS, CSS, fonts) and analytics pings (Cloudflare Insights). Zero requests containing file contents, code snippets, or file paths.
  6. Check the Initiator column to confirm all processing is client-side.

6.2 CLI Packet Inspection

  1. Start a packet capture on the machine that will run the CLI scanner: 
    # Linux/macOS
sudo tcpdump -i any -nn -X 'not port 22 and not port 53'

# Or use Wireshark with display filter:
# tcp and not (tcp.port == 22 or tcp.port == 53)
  2. Run a full repository scan: simplebeacon scan .
  3. Observe: zero outbound TCP/UDP packets to external IPs during the scan. The only network activity (if any) is DNS resolution for the initial page load and Cloudflare analytics beacon.
  4. For air-gapped validation, repeat with the network interface fully disabled.

6.3 Expected Network Activity

The following network requests are expected and legitimate — none contain source code:

  • Static asset requests to simplebeacon.ai (JS, CSS, fonts, images)
  • Cloudflare Insights beacon (anonymous page view analytics)
  • Stripe.js loading (only on pricing/checkout pages)
  • API calls to /api/* (authentication, license validation, billing) — these transmit only tokens and metadata, never source code

7. Air-Gapped Verification

For maximum assurance, SimpleBeacon can be tested in a fully disconnected environment:

  1. Browser sandbox: Enable Airplane Mode or disconnect from the network. Navigate to https://simplebeacon.ai/audit (if cached) or open the local HTML file. Run a scan. All processing occurs in the browser's memory with zero network dependency.
  2. CLI scanner: Disable all network interfaces (sudo ifconfig eth0 down or Airplane Mode). Run simplebeacon scan .. The scanner operates flawlessly offline. License tokens are validated locally via HMAC-SHA256.
  3. Enterprise Air-Gapped deployment: The Docker image is pulled once on a connected machine, then transferred to the air-gapped network via physical media. All subsequent operations require zero internet connectivity.

Reports and certificates are generated locally and saved to the filesystem. No cloud dependency exists for core scanning functionality.

8. Cryptographic Integrity

Every scan report produced by SimpleBeacon can be independently integrity-verified:

  • SHA-256 hash: Computed over the JSON report output. Any tampering with the report invalidates the hash.
  • HMAC-SHA256 signature: The report is signed with the project's license secret. Auditors can verify the signature without logging into SimpleBeacon.
  • Certificate ZIP: Board-ready certificates include the PDF certificate, JSON exports, and a SHA-256 integrity seal in a single ZIP package.
# Verify a report signature
echo -n "REPORT_JSON" | openssl dgst -sha256 -hmac "LICENSE_SECRET"

9. Compliance Framework Alignment

SOC 2 Type II

  • SimpleBeacon's zero-source-upload design can support security and confidentiality controls when deployed and configured appropriately; it is not a SOC 2 certification.
  • Since source code never enters SimpleBeacon's infrastructure, there is no attack surface for source code exfiltration.
  • Annual SOC 2 Type II reports are available for enterprise clients under NDA.

EU AI Act

  • The Compliance Suite produces Annex III high-risk AI system documentation, Article 14 Human Oversight evaluation, and Article 50 transparency checks.
  • All documentation is generated from local scan results — no source code is transmitted to produce compliance artifacts.
  • This is a technical attestation, not a legal certification. For full legal conformity, engage a qualified EU legal firm.

GDPR

  • SimpleBeacon does not process personal data contained in source code. Since source code is never uploaded, any personal data (e.g., email addresses in code comments) remains on the client's infrastructure.
  • Account metadata is processed in the client's chosen region (EU Frankfurt or US Virginia) with no cross-border transfer.
  • A formal Data Processing Agreement is available for countersignature.

10. Automated CI/CD Validation Scripts

SimpleBeacon provides post-deployment verification scripts that client security teams can integrate into their own CI/CD pipelines:

  • verify-production.ps1 — Validates production deployment configuration, CSP headers, and routing rules. Asserts that connect-src matches the documented policy.
  • verify-email-pipeline.ps1 — Validates the email notification pipeline for breach notification readiness.

These scripts can be run as pre-deployment security gates in the client's CI/CD sandbox. They assert zero unexpected egress and can be customized to match the client's network boundary policies.
