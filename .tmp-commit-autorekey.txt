feat(security): autonomous background re-keying worker for quarantine migration

Wire the key rotation store's re-keying migration engine into the
auto-heal timer in audit-logger.cjs. During each 5-minute background
tick, the worker checks if a key rotation is active and, if so,
re-encrypts per-tenant quarantine files from the previous key to the
active key. After successful migration, the previous key is
force-purged from the key ring.

audit-logger.cjs (updated):
- runAutonomousReKeying(): Checks keyRotationStore.getRotationStatus(),
  scans quarantine directory for tenant-* dirs, decrypts each file
  with fallback (tries active key first, then previous), re-encrypts
  with active key, writes back to disk. Force-purges previous key
  after successful migration (0 failures).
- getReKeyStats(): Returns migration statistics (totalSweeps,
  totalMigrated, totalSkipped, totalFailed, totalPurged, lastResult)
- Wired into startAutoHeal() timer tick alongside healAllOrgs()
- Scans both getAllOrgIds() AND quarantine dir for tenant-* dirs
  (healed entries are removed from main log, so getAllOrgIds alone
  would miss orgs with only quarantined data)

crypto-utils.cjs (updated):
- decryptForDirectory() now has multi-key fallback, mirroring the
  existing pattern in decrypt(). After trying the current derived
  directory key, it falls back to derived keys from retired master
  keys (via getDecryptionKeys()). This enables decryption of
  directory-level encrypted files during key rotation.

  window. This enables the re-keying worker to evict the old key
  as soon as all files are confirmed migrated.
